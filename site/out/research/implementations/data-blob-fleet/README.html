implementations/data-blob-fleet — clean-room analyser for opaque data blobs

A general, format-agnostic structural analyser for the fleet's opaque data

blobs — the files that are neither code nor a documented container, where the

only question that matters is *"is this a coefficient table for a format

somebody already specified publicly, or an opaque vendor container?"*. It

answers with measurements, not guesses: header probe, size factorisation,

record-stride autocorrelation, integer/float plausibility, block entropy,

printable-string census, and same-offset diffing. Pure stdlib; the analyser

asserts no structure it has not measured.

Two fleet targets motivated it, one per structural class:

target class (measured) leverage
hrtf5c.bin (ADSP spatial audio) packed binary32 coefficient table 12 devices in the laptop half
dax_param.bin (Dolby DAX tuning DB) 16-byte tag-record container 11 devices (+3 variants on 4 more)

Full findings: data-blob-analysis.md.

Clean-room statement

blob_probe.py was written from (a) public, freely licensed sources and

(b) the author's own measurements of payload bytes fetched from public

repositories. No decompiled code, no disassembler output, no proprietary

header, no vendor documentation and no vendor tool was read. Every claim in

the analysis doc is either a direct arithmetic/histogram/entropy measurement of

bytes on disk or a value quoted from a named public source with an access date.

Claims that no public source resolves are marked [OPEN].

No proprietary payload is committed. The repo .gitignore excludes *.bin,

so fixtures/ holds only synthetic bytes generated by make_fixture.py

from arithmetic and from public models (the Woodworth spherical-head delay

formula for the HRTF-shaped fixture; an invented NATO-alphabet tag vocabulary

for the container-shaped one). test_blob_probe.py verifies the fixtures

regenerate byte-for-byte.

Files

file role
blob_probe.py structural analyser + JSON emitter + CLI (stdlib only)
make_fixture.py deterministic synthetic-fixture generator → fixtures/
fixtures/*.bin synthetic bytes mirroring the two real magnitudes (164,480 B / 34,736 B); gitignored, regenerate with python3 -I make_fixture.py
test_blob_probe.py unittest suite — 54 tests, all passing
data-blob-analysis.md the per-file analysis: byte ranges, decomposition table, verdicts, [OPEN] list

Usage


# one file, human summary
python3 -I blob_probe.py <file> --brief

# full report as JSON
python3 -I blob_probe.py <file> --json out.json

# include up to 4096 binary32 samples
python3 -I blob_probe.py <file> --json out.json --floats

# cross-version diff (the F-75 same-offset method)
python3 -I blob_probe.py a.bin --diff b.bin --brief

Options: --max-stride N (default 256), --strings-min N (default 4),

--blocks N (default 16). Exit status 0 on success, 2 on unreadable input or

bad arguments — the tool validates nothing, so it never exits 1 on content.

What each pass tells you

pass signal for a coefficient table signal for a tag container
floats (binary32 LE) finite ≈1.0, in_physical_range_1e4 ≈1.0, denormals ≈0, distinct ≈1.0 denormals high, distinct very low, "floats" near 1e30
stride byte-equality fundamental at the sample width (=4) only spike at the record size, with a phase profile
entropy flat, high (≈7.4 bits/byte there is no unused alphabet) low (2–3 bits/byte from zero padding)
strings lowercase 4CC 0 hundreds
ints u32 distinct-fraction high (>0.5) very low (<0.1)

None is conclusive alone; the report prints every number so a reader can

disagree with the interpretation.

Test results

python3 -m unittest -v test_blob_probe — 54 tests, all passing

(2026-11-19; analyser and fixtures dated 2026-11-18). Coverage:

  • factorisation arithmetic (both fleet sizes), divisor completeness, grid

decomposition including width-infeasibility rejection;

  • header probe: public magics (HDF5/SOFA storage, OpenAL Soft MinPHR),

4CC extraction, no false positives on random bytes;

  • stride detection on five synthetic strides (8/12/16/24/32), fundamental-vs-

multiple resolution, phase-profile concentration, --max-stride clamp;

  • float plausibility pass and fail, unit-normalised detection, endianness

asymmetry, empty-input safety;

  • integer cardinality both ways; entropy flatness, falling-tail shape, per-block

zero tracking, entropy bounds (0 and 8);

  • string/fourcc extraction and --strings-min;
  • diff mode: identical files, a single localised 160-byte region, unequal

lengths reported not truncated;

  • malformed input: truncated table (odd length), empty file, 1-byte file;
  • CLI/JSON contracts: --brief, --json, --floats, --diff, exit 2 on

missing file and on a bad flag, md5/sha256 agree with hashlib;

  • fixture determinism: regeneration is byte-identical, magnitudes match.

Run with -I for the CLI subprocesses; run the suite as

python3 -m unittest -v test_blob_probe (a bare -I -m unittest strips the

cwd from sys.path).

Value statement

What this buys the program. The fleet's remaining unknowns are mostly

"is there a public spec for this?" — a question that has historically consumed

a session per file. The analyser turns it into four numbers and a

factorisation table, and it separated the two targets here into opposite

answers within minutes:

  • hrtf5c.bin (164,480 B) is a **packed, non-unit-normalised binary32

magnitude/phase table on a 257-bin grid**, and its ITD sweep peaks at 770.8 µs

— inside the physical range of a human head, which is a strong,

format-independent confirmation that it is real HRTF data rather than

opaque vendor state. Its encoding is not SOFA/AES69 (no HDF5/NetCDF

container) and not OpenAL Soft MinPHR (no magic, 32-bit not 24-bit

samples, magnitude/phase not minimum-phase taps) — an honest negative with a

precise positive: the content class is known-public, the encoding is

vendor-specific.

  • dax_param.bin (34,736 B) is a 16-byte tag-record container whose tag

vocabulary, tuning-name table and one large integer array match a **public

GPL-adjacent artifact on the same devices** (dax-default.xml, shipped in

the same vendor tree) byte-exactly — the 20 IEQ band frequencies and their

20 targets are present at identical values. That upgrades the file from

"opaque camera parameter blob" (the task's working hypothesis) to "compiled

form of a readable tuning database", and the device trees themselves file it

under Audio Firmware, not camera.

What it does not buy. The analyser says nothing about semantics: which

DAX tag means what, how the HRTF table is interpolated at runtime, or what a

free replacement must compute. Those stay [OPEN] and are listed explicitly

rather than guessed.
