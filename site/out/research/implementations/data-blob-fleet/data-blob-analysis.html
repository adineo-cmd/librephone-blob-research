Data-blob analysis — real-payload RE of hrtf5c.bin and dax_param.bin (2026-11-18)

The program's first content-level RE of opaque data blobs (as distinct from

containers, firmware overlays and manifests): two high-reuse blobs in the

laptop half, hrtf5c.bin (ADSP, 12 devices, 164,480 B) and dax_param.bin

(34,736 B, 11 devices + 3 variants). Both were located in public repositories,

fetched, **md5-verified byte-exact against the upstream database (5/5 distinct

md5s MATCH)**, and run through the lab's clean-room analyser (blob_probe.py,

54/54 fixtures passing). This file documents what the real bytes actually

contain, per byte range.

No payload bytes are committed here. Payload files live only under

/tmp/dbfleet_payloads/ and are re-fetchable via the route log in §1.3;

everything below is derived structural fact. Fixtures are synthetic and

regenerated by make_fixture.py.

Clean-room statement: blob_probe.py was written from public format

documentation and the lab's own measurements only. No decompiled code, no

proprietary documentation, and no vendor source was consulted. Every numeric

claim below is either a measurement over the payload ([measured]) or a match

against a public licensed artifact ([public-match]); anything unresolved is

marked [OPEN].

2. hrtf5c.bin, 164,480 B — the magnitude/phase table family

md5 2a47164eed5282f27ad503a28c7b71a0. Bytes identical from marble,

cupid, and nuwa's odm/etc/audio/ copy.

2.1 Container verdict: none

[measured] No magic number. No HDF5 (\x89HDF), NetCDF (CDF), RIFF,

MinPHR, or ASCII SOFA signature anywhere. Entropy 7.395 bits/byte with a

flat block profile (16 blocks, 7.30–7.43) — i.e. homogeneous content, no

header region and no trailer. 874 zero bytes (0.53%); all 256 byte values

present; 200 printable runs ≥4 chars but 0 lowercase 4CC tags. This is a

bare numeric table with no self-description at all — the opposite of the §3

file.

2.2 Size decomposition

[measured] 164,480 = 2^7 × 5 × 257 (32 divisors). The decisive reading is

160 × 257 × 4 B:


160 records × 257 float32  =  40 directions × 2 ears × 2 components
                              × 257 bins × 4 bytes

The 257 is the giveaway: it is N/2 + 1 for N = 512, i.e. a **one-sided

spectrum** on a 512-point FFT grid. 160 = 40 × 4 gives 40 directions with

four records each. Nothing else in the divisor set produces a

spectrum-shaped factor, so this decomposition is over-determined rather than

merely plausible.

2.3 Record layout: alternating magnitude and phase rows

[measured] Reading the file as 160 rows of 257 little-endian binary32:

  • Rows at even index (80 rows): every value ≥ 0. Global range

0.0001 … 12.3030.

  • Rows at odd index (80 rows): every value ≤ 0. Global range

−185.35 … 0.00.

There are zero exceptions in 160 records. That parity split is the

strongest single structural fact in this file: the two components are stored

as separate rows, not interleaved as complex pairs. A complex-interleaved

layout would not produce an exact all-non-negative / all-non-positive row

alternation.

The 4-row group is therefore:

offset in group row kind meaning
+0 magnitude, ≥ 0 ear 1 magnitude
+1 phase, ≤ 0 ear 1 phase
+2 magnitude, ≥ 0 ear 2 magnitude
+3 phase, ≤ 0 ear 2 phase

with 40 such groups.

2.4 Float32 verdict: a coefficient table, not unit-normalised data

[measured] Over all 41,120 binary32 words: 100% finite, 100% within ±1e4,

0 denormals, 40,984 distinct (99.7% unique). Only 25.7% fall inside

[−1, 1].

That last number rules out the obvious guess that these are normalised

filter taps or a probability-like field. Combined with the magnitude rows

being strictly non-negative and centred near unity, the natural reading is a

linear gain table: DC magnitude per direction runs 1.031 … 1.130, mean

1.079. A unit-energy-normalised HRTF would have its DC term near 1.0 only

by coincidence and would show values below 1 across most of the band; this

table instead sits above 1 nearly everywhere in the low bins and decays

toward the top.

2.5 Phase rows: linear-ish, not exactly linear

[measured] Each phase row is dominated by a linear ramp. Fitting a straight

line to each of the 80 phase rows:

  • slope: −0.7316 … −0.2797 rad/bin
  • span (row[256] − row[0]): −185.4 … −69.1 rad
  • residual RMS from the straight line: 0.78 … 3.98 rad, mean 1.82 rad

So the rows are not pure linear phase — the residual is 1–4 rad, which is

far above float noise. And only 9 of 80 rows are monotonically

non-increasing; the rest contain a median of 3 local increases. The correct

statement is "a phase response whose dominant term is a delay ramp, plus a

real minimum-phase component", not "linear phase". An earlier working note in

this pass claimed all 80 rows were strictly decreasing; that was wrong and is

corrected here.

2.6 Delay structure: two ears per direction, anti-correlated

[measured] Converting each phase row's end-to-end span into a group delay at

N = 512, fs = 48 kHz:


delay_us = −(span / (bins−1)) × N / (2π · fs) × 1e6
  • per-row delay: 458.3 … 1229.2 µs
  • pairing row +1 with row +3 inside each 4-row group gives 40 pairs whose

mid-delay is tightly clustered: mean 773.7 µs, sd 32.9 µs, range

708.3 … 843.8 µs

  • within a pair the two ears are strongly anti-correlated (r = −0.955)

That is exactly the signature of a two-ear pair sampling the same direction:

both ears share a common propagation delay (the 773.7 µs mid), and the

difference between them is the interaural time difference.

Interaural time difference per direction:

  • range −770.8 … +645.8 µs
  • peak |ITD| = 770.8 µs
  • best single-harmonic fit over the 40 directions: amplitude 599.0 µs,

RMS residual 53.5 µs, one full cycle across the 40 directions

[measured] The peak 770.8 µs is at the physical ceiling for a human head

(Woodworth's spherical-head model gives roughly 800 µs for a 0.0875 m

half-spacing at 343 m/s). A one-cycle sinusoid over 40 directions is what you

get when the directions are a single azimuth sweep, and the residual is small

enough that the sweep is close to uniform. The file therefore encodes **40

azimuth positions around the head, 2 ears, 257 one-sided bins**.

2.7 Verdict for this family

Content class: known-public HRTF — magnitude/phase on a 257-bin one-sided

grid, 40 directions, 2 ears. [public-match] The content class (head-related

transfer function, magnitude and phase, 512-point grid) is standard published

DSP; the Woodworth model and the SOFA/AES69 conventions are public.

Encoding: vendor-specific. [measured] It is not SOFA (no HDF5/NetCDF

container, no ASCII header, no Data.IR/Data.SamplingRate variables) and

not the OpenAL Soft HRTF layout (that file is chunk-tagged and stores

16-bit or float IRs behind its own header; this file has no tags at all). The

format is a flat vendor table whose parameters have to be supplied out of

band. Evidence class: measured.

3. hrtf5c.bin, 54,180 B — the self-describing container family

md5 630a2e1853c80e1dd1d2b1cd2d334ac4, vermeer only. **Completely different

family from §2** — same filename, unrelated format.

3.1 Chunk chain

[measured] A 4-character-code chunk stream, tag + u32 payload repeated.

Full walk, offsets are file offsets:

offset tag payload / meaning
0 VER0 12 bytes of version words
16 DATE 2023, then len 4, then 24
32 TYPE M80X (a 4CC type code)
40 DIM0 3
48 SPKN 13
56 LSGN 15
64 SDIR 26 float32 direction angles
171 BLSG 80, 768
356 INVM float32 matrix, starts 1.732051 (= √3), −1.0, −0.517638
900 FFTN 512
908 HLEN 256
916 SMPR 48000
924 HRTF 53,248 B of float32
54176 ENDM terminator (4 bytes, file ends)

SPKN = 13 speakers/directions, LSGN = 15 loudspeaker gains,

FFTN = 512, HLEN = 256, SMPR = 48000.

3.2 Arithmetic check — exact

[measured] HRTF body is 54176 − 928 = 53,248 bytes. And:


13 directions × 2 ears × 512 taps × 4 B  =  53,248   ✓ exact

Note the correction against an earlier working note in this pass, which read

the body as 26 × 2 × 256. The header says SPKN = 13 and FFTN = 512, and

13 × 2 × 512 lands on the byte count exactly, so the body is **13

directions × 2 ears × 512 taps**. 26 × 2 × 256 happens to give the same

product, which is why the ambiguity had to be resolved from the header fields

rather than from the size alone.

SDIR holds 26 float32 values at offset 68: `30, −30, 0, 60, −60, 90, −90,

150, −150, 46, −46, 134, −134, 0, 0, 0, 0, 0, 0, 0, 0, 0, 46, 46, 46, 46`.

That is 13 azimuth pairs (a left and a right for each speaker) plus trailing

padding — consistent with SPKN = 13 and 2 ears.

INVM begins 1.732051, −1.0, −0.517638 — √3, −1, and a value consistent

with a 3×3 or 4×4 normalisation/inversion matrix. BLSG gives 80 and 768,

which is 80 × 768 = 61,440 — the same order as the body, suggesting a

block/gain description [OPEN: exact semantics of BLSG].

3.3 The 451,512 B build

[measured] PixelOS-Nuwa/Nuwa-Dump vendor/etc/hrtf5c.bin. Same chain

through HRTF, but:

  • TYPE = M2XX (vs M80X)
  • DATE payload length 12 (vs 4)
  • after HRTF comes RVBL → RVBC → RVBD instead of ENDM

Reverb chunk arithmetic resolves exactly:


RVBL = 49664 (float count)
RVBC = 2     (channel count)
RVBD = data
49664 × 4 B × 2 channels + 24 B of chunk headers = 397,336
54176 + 397,336 = 451,512 = file size   ✓ exact

The two channels are laid end to end: the second starts at

54200 + 49664 × 4 = 252,856 and runs to EOF. So the 451 kB file is the same

HRTF container with a two-channel reverb tail attached, not a different

format.

3.4 Verdict for this family

[measured] A self-describing vendor HRTF container: 4CC-tagged, with

explicit FFT size, hop length, sample rate, speaker count and direction

angles, then a float32 impulse-response body. It is far more tractable than

§2 — everything needed to interpret the body is in the header. Which DSP path

consumes which of the two families is [OPEN]; the fact that they coexist

under one filename, and that vermeer ships the tagged one while 11 other

devices ship the flat one, suggests a generation change in the audio stack

rather than two roles.

4. dax_param.bin, 34,736 B — a compiled Dolby DAX tuning database

Four md5 variants, all 34,736 B. The analysis below is on

70727b648c00a14bad7ede05ba9b4bd3 (beyond0lte) unless stated.

4.1 Container verdict

[measured] No magic. Entropy 2.775 bits/byte, 62.95% zero bytes,

only 116 distinct byte values, and a falling-tail block profile

(2.71 → 2.08 across 16 blocks) — the shape of a header plus repetitive records

plus a dense tail, not homogeneous numeric data.

Header, u32[0..6]:


9, 706, 342, 0, 148, 0x40000000, 0x6e6f6569 ("ieon" as LE chars)

u32[0] = 9 is load-bearing (see §4.3). u32[4] = 148 and

u32[5] = 0x40000000 recur throughout the record stream as field values.

u32[1] = 706 and u32[2] = 342 were tested against every count and offset

that suggested itself and match none of them

(34736/706 ≈ 49.2, 706 × 16 = 11296, no offset lands on a record

boundary) — [OPEN: meaning of header words 1 and 2].

4.2 Record format: 16-byte header + variable payload

[measured] Records are [4-byte lowercase tag][u32 a][u32 b][u32 c]

followed by a payload. Scanning with that rule over the whole record region

(0–25,928) gives 855 records in 37 distinct tags. The gap between

consecutive record starts is always a multiple of 4, and the distribution is:

gap count implied payload
16 401 0 (header only)
24 9 8
32 119 16
40 45 24
44 108 28
48 162 32
104 9 88
176 1 160

So the record is header + gap − 16 bytes of payload, and payloads are

small and highly quantised (0, 8, 16, 24, 28, 32, 88, 160 bytes). The one

176-byte record is iebs — the frequency/target table of §4.5.

Tags are space-padded to 4 bytes where the name is short (iea , vol ,

plb , dsb , vmb ). A scanner that requires all four bytes to be

lowercase letters misses these; the correct rule is "strip trailing spaces,

then require 1–4 lowercase letters".

4.3 Nine groups, 2,824 bytes each

[measured] u32[0] = 9 is the group count. Nine groups start at

512 + k × 2824 for k = 0..8:


512, 3336, 6160, 8984, 11808, 14632, 17456, 20280, 23104
25928 = 512 + 9 × 2824   (group region ends here)

Every one of the nine groups begins with the same record — tag vssd, fields

(1, 4, 2) — which is what makes the boundary detection unambiguous. Each

group contains exactly 93 records, giving 9 × 93 = 837 inside the group

region plus 18 in the 0–512 header region = 855 total.

[measured] Groups 1–8 are tag-sequence identical. Group 9 differs in

one place only: its sixth 14-record section (§4.4) carries the tuning-table

tags instead of the equaliser tags. Byte-level, groups 1–8 differ from each

other by only 14–40 bytes out of 2,824 (0.5–1.4%) — those deltas are per-profile

values, not structure. Group 9 differs from group 1 by 238 bytes.

4.4 Internal layout of a group: 6 × 14 + 9

[measured] Within each group, the 93 records split as:

  • six sections of 14 records (84), each section carrying a single

power-of-two selector in field c

  • a 9-record tail

Sections 0–4 are identical in tag order across all nine groups, and their

selector values cycle 2, 8, 128, 16384, 32768 in every group. Section 5 is

where groups 1–8 and group 9 diverge:


groups 1–8 §5: vssd avsb svrc hvrc bmde ieon mdee mdle miee msce mave dvme rvse rvsa
group  9   §5: vssd avsb svrc hvrc bmde geon iebs avon bexe dhsa dfsa dhfm aoon dvlc

[measured] Field c is a bitmask/selector, not a length: it takes only

16 distinct values, and the six section-start values `2, 8, 128, 1024, 16384,

32768` are all single bits, appearing identically at the same position in all

nine groups. The remaining common value is 0x40000000 (73 records), the "on"

state of the enable-style tags. Field a is almost always 1 (746 of 855

records), with 8 for the 108 svrc/hvrc records and 41 for the single

iebs record. Field b is the value word: only 19 distinct values, dominated

by 0 (339), 1 (119), 103 (108), 256 (54), 6 (54) and 4 (48), plus

109 records holding signed parameters as two's complement (−496 up to

−16, e.g. 4294967040 = −256).

4.5 Decisive match: the blob contains the public Dolby tuning database

[measured] + [public-match] This is the result that settles what the file

is. Tag iebs at offset 25,456 has fields (41, 20), followed by a

20-int ascending frequency array at 25,468 and a 20-int target array at

25,548.

Both arrays are byte-identical to the <ieq-bands> table in the public

proprietary/vendor/etc/dolby/dax-default.xml from the same device tree:

blob (iebs @25468 / @25548) public XML <band_ieq>
frequencies 47, 141, 234, 328, 469, 656, 844, 1031, 1313, 1688, 2250, 3000, 3750, 4688, 5813, 7125, 9000, 11250, 13875, 19688 identical, in order
targets 157, 167, 218, 218, 203, 188, 192, 192, 205, 213, 218, 209, 193, 159, 134, 97, 71, 22, −90, −283 identical, in order

Verified programmatically as exact tuple equality on both arrays, over all

20 bands.

Three further corroborations:

  1. u32[0] = 9 ↔ 9 <profile> entries. The XML has exactly nine

profiles: `Dynamic, Movie, Music, Voice, Game, Off, Game1, Game2,

SpacialAudio`. The blob has exactly nine groups of identical shape.

  1. Tuning-name table at 26,796. Count word 3, then three 32-byte

NUL-padded name records each followed by two u32:

speaker (1,2), bluetooth (2,2), bluetooth_spatialAudio (0,26).

All three names appear verbatim as <tuning name="…"> elements in the

XML, and bluetooth_spatialAudio is a distinctive enough string that the

match is not coincidental.

  1. aobs at 27,128 holds a 62-word u32 array beginning

20, 2, 47, 141, 234, … — the same band table re-encoded with a leading

count and channel word.

Tag vocabulary is systematic 4-letter 2-feature + 2-parameter coding, e.g.

ieon/iea /iebs (IEQ), bexe/dsa /dhsa/dfsa/dhfm (dialog

enhancer), aron/arde/arsa/artp/aobs/arbs/arod (audio

optimizer), dvlc/dvle/dvla/dvli/dvlo/dvme/dvmc (virtualizer),

plus vol , beon, deon, ngon, vssd, hvm , svm , avsb, svrc,

hvrc, bmde, ceon, ceqt, rssa/rsse, plb , mvbe, dplp, vmb ,

dom , spea/ker , blue/toot/spat/ial /udio. The name-table

tags are visibly the name strings being scanned as tags (spea+ker =

speaker, blue+toot = bluetooth), which is a good reminder that a

naive 4CC scan over this file will always over-count.

4.6 Verdict for this target

**A vendor container holding a compiled form of a publicly readable Dolby DAX

tuning database.** [public-match] The frequency and target arrays are

byte-identical to the public XML; the profile count matches; the tuning names

match; the tag vocabulary maps onto the XML's element vocabulary. Evidence

class: measured + public-artifact match.

Not camera tuning. The task's premise is corrected: this is audio

(Dolby DAX / libswdap), filed under ## Audio Firmware, and its contents

are the audio tuning database.

5. Cross-version diffs (F-75 same-offset method)

[measured] All four dax_param.bin variants are the same size, so the

same-offset comparison is meaningful.

pair identical bytes
beyond0lte ↔ d1 99.66%
beyond0lte ↔ d2s 99.63%
beyond0lte ↔ r8q 99.84%
d1 ↔ d2s 99.86%
d2s ↔ r8q 99.69%
d1 ↔ r8q 99.61%

[measured] beyond0lte ↔ d1 differs in 119 bytes across 13 runs, all

inside the single span 27,225–27,383. That span is a table of 40-byte

records of signed values (00 00 00 ff, 62 ff ff ff, a5 ff ff ff).

The region is all zeros in beyond0lte and r8q but populated in d1 and

d2s. That is a per-device tuning table, not a structural field — which is why

the diff localises so tightly while the rest of the file is 99.6%+ shared.

[measured] All four variants share the iebs frequency and target arrays at

identical offsets 25,468 and 25,548. The nine-group skeleton at 2,824 B

stride is also present in all four. So the per-device variation is confined to

value regions, and the format is stable across the whole Samsung set.

[measured] dax-default.xml itself is not identical across devices:

116,575 B for beyond0lte, 116,623 B for d2s. Do not assume one canonical XML

when cross-checking.

6. What this means for a free reimplementation

Tractable today, no proprietary bytes needed:

  • hrtf5c.bin (54,180 B family). Fully self-describing: a free reader is

a 4CC chunk walk plus struct.unpack of the HRTF body as

13 × 2 × 512 float32. A free writer can emit the same chunks from any

public HRTF dataset. The only unknowns are the semantics of BLSG and

INVM [OPEN].

  • dax_param.bin. The record framing (16-byte header, tag + 3 u32,

variable payload), the nine-group skeleton at 2,824 B, the six-section

layout, and the bitmask field are all pinned by measurement. The semantic

content is recoverable from the public dax-default.xml, which is a

licensed public artifact shipped in the same tree — so a free tuning

database can be generated from the XML rather than copied from the blob.

Needs synthesis or further RE:

  • hrtf5c.bin (164,480 B family). The content class is public (HRTF

magnitude/phase, 40 azimuths, 257 one-sided bins) and the geometry is

measured, so a free replacement can be synthesised from a public HRTF set

or a spherical-head model. What is not public is the exact vendor encoding

choices — but §2.3–2.6 pin the layout tightly enough that the encoding is

reconstructible: 4-row groups, magnitude rows non-negative, phase rows

non-positive, group delay from the ramp, ITD from the pair difference.

  • Header words 706 and 342 in dax_param.bin [OPEN].
  • BLSG/INVM semantics in the tagged HRTF container [OPEN].
